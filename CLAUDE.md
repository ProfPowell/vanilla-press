# Vanilla Press

A platform-first content system where the component model, the editor, the storage, and the output are all built on web standards.

## What This Is

Vanilla Press stores content as a typed block AST that maps 1:1 to a web component model. A `callout` block in the content store is the same `callout` that exists as a Vanilla Breeze `<status-message>` element in the browser, for example, the same `callout` that renders as `> **Warning:**` in markdown output. One concept, multiple serializations, no lossy conversion.

Vanilla Press edits content and syncs it into a Cook site; Cook builds the static output served from Cloudflare Pages. A thin Cloudflare Worker handles content negotiation — same URL serves HTML to browsers, markdown to LLM agents, JSON to API consumers, and HTML fragments to html-star (hypermedia) requests.

## Architecture

```
content-schema.js          ← single source of truth for block types
        │
        ├── renderers/     ← pure functions: AST → string
        │   ├── html.js    ← semantic HTML with custom elements
        │   ├── markdown.js← clean markdown with frontmatter
        │   └── feed.js    ← RSS/Atom
        │
        ├── store/         ← SQLite/D1 content API
        │   └── content.js
        │
        ├── sync/          ← syncs JSON + HTML pages to and from a Cook site
        │   ├── to-site.js ← store → site (one document)
        │   └── from-site.js ← site → store (startup, sync --from-site, reload)
        │
        └── worker/        ← Cloudflare Worker
            └── index.js   ← content negotiation + scope routing
```

## Key Concepts

**Block AST:** Documents are JSON arrays of typed blocks. Blocks have `type`, optional `attrs`, and `children` or leaf `value`. The schema in `content-schema.js` defines all block types and is shared across the entire system.

**Rendering Scope:** Every piece of content renders at one of five scopes: `page` (full HTML document), `content` (article body only), `block` (single block), `collection` (list of document cards), `meta` (document metadata). The scope is a function parameter, not a code path. This eliminates the template duplication problem that htmx/hypermedia integrations normally suffer from.

**Content Negotiation:** The Cloudflare Worker reads `Accept` headers and `X-Star-Request` (html-star) headers to determine format and scope. Static files are pre-generated by the Cook build for common scopes. Dynamic queries (search, arbitrary filters) hit Cloudflare D1.

## Tech Stack

- **Language:** Vanilla JavaScript (ES modules, no TypeScript, no build step for client code)
- **Storage:** SQLite locally via better-sqlite3, Cloudflare D1 in production
- **Deployment:** Cloudflare Pages + Workers
- **CSS:** Vanilla Breeze — native @layer, @import, custom elements as style hooks
- **Testing:** Node.js native test runner (`node --test`)
- **Editor (future):** ProseMirror with custom NodeViews rendering Vanilla Breeze components

## Coding Conventions

- ES modules throughout (`import`/`export`, no CommonJS except where Node requires it)
- Named exports only, no default exports
- Pure functions for renderers — no side effects, no state
- JSDoc for public APIs
- camelCase for variables/functions, PascalCase for classes, kebab-case for custom elements
- No frameworks, no ORMs, no build tools for application code
- SQL is fine — write it directly, no query builders

## Using Vanilla Press with a Cook site

Words, used the same in code, CLI and UI: **sync** = VP writes a document's files into the site (or, `--from-site`, loads the site's JSON into the store); **publish** = a document's status (published documents get an HTML page); **build** = Cook turns `src/` into `dist/`; **deploy** = shipping `dist/` to hosting (not VP's job).

Vanilla Press no longer builds a site itself. It edits content and syncs files into a [Cook](https://github.com/ProfPowell/cook) site; Cook builds and serves it.

- Point at a site with `--site <path>` or `VP_SITE=<path>`. Without one, Vanilla Press runs in fixture mode (the repo's own `content.db` and `media/`) and sync is disabled.
- Layout inside the site:
  - `.vp/content.db` (store) and `.vp/manifest.json` (what this machine last wrote or imported: JSON hashes plus path hints). Both are machine-local: add `.vp/` to the site's `.gitignore`.
  - `src/media/<file>` (uploads)
  - `content/<collection>/<slug>.json` (document source), `content/media.json`
  - `src/<path>/<slug>.html` (published pages: front matter plus bare block HTML; posts use `layout: "post"`; the last front-matter key, `vp_id`, names the document that owns the page)
  - `config/vp.json` (settings)
- Commit `content/` and `src/`. The editor/server syncs the store from `content/` on startup, so pulled edits come in; `vp sync --from-site [--replace]` does the same from the CLI.
- `vp sync` writes every document to the site (`POST /api/sync` does the same). Saving in the editor syncs that document. Drafts and archived documents get JSON only. Re-run `vp sync` after changing the `collections` config.
- Generated HTML pages are overwritten on sync and removed on rename/unpublish/delete; don't hand-edit them. Vanilla Press only overwrites or removes a page whose `vp_id` is the document's own id (a JSON file: whose `id` is), so hand-written pages are never touched (saving onto one is refused).
- Cook interpolates `${...}` in page HTML, so the synced body is protected (the JSON keeps the text as written): code blocks are written as `<code-block data-escape>` with their raw code (Cook stores it before interpolation and escapes it itself), and elsewhere `${` is written as `$<!---->{`. Known limitation: a code sample containing the literal text `</code-block>` ends the block early.
- Collection names `layouts`, `includes`, `components`, `media` and `assets` are reserved.
- If a JSON file changed on disk (git pull, hand edit), saving returns a conflict; use "Load the version on disk" in the editor.
- `vp serve` (and `npm run dev`) default to port 3007; `cook dev` defaults to 3000. Preview with `cook dev` in the site: the editor's Preview button opens the `preview_url` config value (default `http://localhost:3000`).
- Old `content/.vp-manifest.json` files are obsolete and ignored; delete them. Pages synced before `vp_id` existed have no owner: delete them and run `vp sync`.
- Site layouts (`src/layouts/post.html`, `page.html`) and `collections: { html: true }` in the Cook config are the site's responsibility.

## App

`vp` (or `vp app [--port <n>]`) starts the app: sites list, then posts, editor and Publish, in the browser at `http://127.0.0.1:3007` (next free port if taken; `VP_NO_OPEN=1` skips opening the browser). `vp serve --site <path>` still starts the single-site editor server as before.

- **Registry:** the sites the app manages are in `~/.config/vanilla-press/sites.json` (override the directory with `VP_CONFIG_DIR`; tests always do). A folder is a site when its `package.json` has `cook-ssg` in `dependencies` or `devDependencies`.
- **Routes:** registry routes are `GET`/`POST /api/sites`, `POST /api/sites/clone`, `DELETE /api/sites/:id` (flushes the site's backup, after any running publish, then forgets it; the folder stays), `POST /api/sites/:id/preview`, `GET /api/folders`; each site's document API is under `/api/sites/<id>/...`; a site's uploads are served at `/sites/<id>/media/<file>`. See `docs/EDITOR.md`.
- **Localhost only:** the server listens on `127.0.0.1`; requests need `Host` of `127.0.0.1:<port>` or `localhost:<port>`, and writes need a same-origin (or absent) `Origin`.
- **VP-owned paths:** a backup stages only `content/`, `src/media` and `config/vp.json` (`BACKUP_PATHS`), never a page. Publish, Update and Unpublish stage those plus one post's pages (`postPages` in `src/app/site-git.js`): its current page, and every page tracked in HEAD whose `vp_id` is that post's, that is modified or deleted in the working tree, and whose working file is gone or still that post's (an old slug after a rename, the page an unpublish removed, also from an earlier run; an old slug another post took since is not staged). A git error while listing them fails the action and reverts its status (nothing committed); only a repo with no commit yet counts as no pages. Never another post's page, never a collection folder wholesale, never `git add -A` on the tree, so your own uncommitted work (a hand-written `src/posts/mine.html`, a layout, `config/main.js`) is never committed. Document writes (create, save, reload, delete, sync-all) wait while a Publish/Update/Unpublish runs, so nothing changes between the build check and the commit. Paths are passed to git literally (`GIT_LITERAL_PATHSPECS=1`).
- **Publish / Update / Unpublish:** runs the site's `npm run build` (install first if there is no `node_modules`); a failed build reverts the status change and commits and pushes nothing. Otherwise it commits and pushes; GitHub triggers the Cloudflare deploy. **Update** is Publish on an already-published post (`POST .../documents/:id/update`, which refuses a draft with 422; `POST .../publish` on a published post is an Update too): it keeps the `published` date and commits `Update: <title>`. If the remote moved, VP rebases once; if GitHub changed files you are also editing outside VP, it refuses up front and leaves the repo untouched.
- **Commit messages:** backups are `Draft: <title>[, <title>] [CI Skip]` when every save in the batch was a draft, else `Edit: … [CI Skip]` (up to three titles, then `and N more`); `Publish: <title>`, `Update: <title>`, `Unpublish: <title>`.
- **Backup:** saves are committed and pushed 30 s after the last save (at most 120 s after the first unpushed one). Every backup carries `[CI Skip]` and holds no page, so **backup commits never change the live site** (and Cloudflare spends no builds on them). **Edits to a published post go live only when you click Update**: saving still rewrites its page in the working tree, so Preview (`cook dev`) shows the edit, but nothing commits that page until Update. The editor says "Saved · not live yet" / "Backed up · not live yet" and clears any "Live" link; `GET /api/sites/<id>/documents/<docId>/state` returns `{ notLive }` so the hint survives a reload. A published post's JSON in git can therefore run ahead of its live page (by design). `GET /status` has `lastPushKind` (`draft`: backups only, or `publish`: a publish/update/unpublish). **Preview** shows published pages only.
- **Second machine:** opening a site runs `git pull --ff-only` first when it has an upstream and no uncommitted changes in the backup paths (a held page edit does not block it; git refuses a fast-forward that would overwrite one) (otherwise, or on any failure, it opens as is), then syncs from the files. A backup or publish push that had to rebase re-syncs the store. A rebase conflict is never left behind: the error names the files and the next step.
- **Live check:** `GET /api/sites/<id>/documents/<docId>/live` compares the deployed page's text with the page the last Publish/Update built (kept in memory per post, so a later `dist/` rebuild by Preview does not count; after a restart it falls back to `dist/`); the client polls every 10 s and gives up after 300 s ("Still deploying, check Cloudflare").
