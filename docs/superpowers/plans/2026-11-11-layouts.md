# Layouts (phases 1–3) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Cook gets layout format 1 (checker, `cook check-layouts`, inheritance, `data-if`/`data-unless`) and a Vanilla Breeze starter set. Vanilla Press gets a per-document layout choice, region block areas and `imageAlt`.

**Architecture:**
- **The checker.** One parser/checker module in Cook (`scripts/utils/layouts/`) is published as `cook-ssg/layouts`.
- **The build.** It renders layout chains through one shared function, `renderLayout`, used by both the HTML-page and markdown paths. Conditionals are decided at layout time where the data is known. A late page-loop pass handles what includes and components bring in.
- **Vanilla Press:**
  - VP loads the checker **from the site's own installed Cook**, so what it checks is what builds the site.
  - It stores `meta.layout` and `regions`.
  - It publishes regions as `<template slot>`.
  - It edits regions as `region` nodes in the existing ProseMirror document.

**Tech Stack:** Node 25 ESM, node:test, linkedom (Cook already depends on it), better-sqlite3 (VP), ProseMirror (VP editor).

**Spec:** `docs/superpowers/specs/2026-11-11-layouts-design.md` (ecda681). Read it before any task.

## Review Focus

1. **Page or region content that contains `<main>`, `<template>`, `<template slot>` or `${`** is never treated as layout structure. It reaches the page verbatim. Pinned in Task 3.
2. **Switching a document's layout back and forth** never loses region content. Regions the new layout doesn't offer stay, marked `Not shown by this layout`. Pinned in Task 11.
3. **A site using none of the new features** builds byte-identically before and after. Pinned in Task 5, against Cook's docs-site and a copy of thomasapowell.com.
4. **A site whose installed Cook has no `cook-ssg/layouts`** still opens in the editor. It shows the old-Cook warning, lists plain layouts, and marks child layouts unusable. Pinned in Task 9.
5. **A document whose layout file was deleted** keeps its value. The select shows `<name> (missing)`, and publishing still writes that `layout:`. Pinned in Task 10.

## Rulings made while planning (deviations from the spec's text)

- **P1. VP loads the checker from the site's Cook**
  (`<siteDir>/node_modules/cook-ssg`), not VP's own dependency.
  - This replaces the spec's "own dependency plus version check". The
    checker always matches the Cook that builds the site, and "too old" is
    simply "the export is missing".
  - *Cost if wrong:* a site with no `node_modules` gets only the fallback
    scan.
- **P2. VP writes every non-empty region** as `<template slot>`, not only
  the ones the layout offers.
  - Cook ignores slots a layout doesn't use, so the sync step doesn't need
    the layout listing.
  - *Cost if wrong:* hidden region HTML sits unused in the page source.
- **P3. "Not shown" regions are shown with a note, not collapsed.**
  - ProseMirror content inside `<details>` is fragile.
  - *Cost if wrong:* longer documents after a layout switch.
- **P4. `imageAlt` is taken from the media library** (the alt of the item
  that `meta.image` names) when the page is written. There is no new
  editor field.
  - *Cost if wrong:* a featured image used by URL with no library row gets
    no alt.
- **P5. Conditionals on markdown page fields are decided at layout time.**
  - An include on a markdown page can't test page fields, because by the
    page loop they are gone. It sees them as empty.
  - *Cost if wrong:* the include's conditional section silently disappears
    on markdown pages.
- **P6. An include counts as a format-1 fragment only when it begins with
  `<!-- layout-fragment -->`.** Otherwise it is plain, like a layout with
  no info block.
  - Without the marker, existing free-form includes would fail
    `cook check-layouts`.
  - *Cost if wrong:* one comment line per include.

### Task 1: Format-1 parser and `checkLayout`

**Files:**
- Create: `scripts/utils/layouts/vocabulary.js`, `scripts/utils/layouts/parse.js`, `scripts/utils/layouts/check.js`
- Test: `test/layouts-check.test.js`, fixtures in `test/fixtures/layouts/`

**Interfaces:**
- Produces:
  - `vocabulary.js` exports `FORMAT`, `PAGE_LAYOUTS`, `DOCUMENT_FIELDS` (Global Constraints), and `HEAD_ELEMENTS = ['meta','link','title','script','style','base']`.
  - It also exports the element sets from the spec's block table: `TEXT_ELEMENTS`, `INLINE_ELEMENTS`, `SECTIONING`, `MENU_ELEMENTS`, `GLOBAL_ATTRS`.
- `parseLayoutSource(html: string, { fragment?: boolean }) → { document, kind: 'base'|'child'|'fragment', info: object|null, infoError: string|null, parent: string|null, lineOf(el): number }`
  - kind is `child` when `<html>` or `<body>` has `data-template`, `base` when the source has `<!doctype`, `<html` or `<head`, and `fragment` otherwise (or when `fragment: true`).
- `checkLayout(html, { fields = [], lists = [], fragment = false }) → { ok: boolean, kind: 'base'|'child'|'fragment'|'plain', info, parent, slots: string[], fields: string[], problems: Array<{ line: number, message: string }> }`
  - `fields` holds extra known field names (site and declared fields).
  - `lists` holds extra list-source roots (top-level data array keys).
  - A base or child with no info block returns `kind: 'plain'`, `ok: false`, `problems: []`. `slots` and `fields` are still filled by a regex scan of `${slot:x}` and `${x}`.

  - `correct base`: the spec's base example plus an info block declaring `slots.aside` gives `ok: true`, `kind: 'base'`, and `slots` `['aside']`.
  - `correct child`: the spec's child example gives `ok: true`, `kind: 'child'`, `parent: 'base'`, and `slots` `['aside']`.
  - `plain layout`: thomasapowell-style `post.html` with no info block gives `kind: 'plain'`. Its slots and fields are scanned.

  - `expression`: `${a + b}` and `${{x}}` are each a problem.

  - `bad page layout`: `data-page-layout="weird"` is a problem, and `${pageLayout}` is ok.
  - `bad info JSON` and `format: 2` are problems at the script's line.
  - `line numbers` survive comments and multi-line attributes. Assert the exact line.

### Task 3: Inheritance, info stripping, nesting-aware slots

**Files:**
- Create: `scripts/utils/layouts/render.js`
- Modify: `scripts/plugins/apply-template.js` (use `extractSlots` and `renderLayout`), `scripts/plugins/process-markdown.js` (`applyLayout` uses `renderLayout`), `scripts/build.js` (pass `data` to `applyTemplate`)
- Test: `test/layout-inheritance.test.js` (unit), `test/layout-inheritance-build.test.js` (end to end)

**Interfaces:**
- Consumes: `parseLayoutSource` (Task 1).
- `extractSlots(html: string) → { content: string, slots: Record<string,string> }`
  - It handles top-level `<template slot="x">` elements with nested `<template>` inside them.
  - It replaces the regex in `apply-template.js` `extractPageData`. Output must be byte-identical when there's no nesting.
- `renderLayout(name: string, pageData: object, { loadLayout: (name) => Promise<string|null>, data?: object, conditionals?: (html, pageData, data) => string }) → Promise<string|null>`. It returns null when `name` isn't found, which keeps the current fallbacks.
  - **Base:** remove the info block, run `conditionals` if provided (Task 4; identity until then), then `renderTemplate(layout, pageData, { removeUnmatchedSlots: true })`.
  - **Child:** parse the **raw child source**, never the filled output, into these parts: the parent, the body `data-*` attributes (except `data-template`, camelCased), the info block (dropped), the top-level `<template slot>` pieces and the remaining body.
    - Run conditionals on each piece, then interpolate it with `pageData`.
    - Recurse into the parent with `{ ...pageData minus every 'slot:*' key, ...attrs, content: renderedBody, ['slot:'+x]: renderedPiece }`. A piece that is empty after trimming is omitted.
  - **Limits:** depth at most 5. A repeated name throws `Error('Layout cycle: post → base → post')`.
  - `loadLayout` uses the existing caches (`store.cachedLayouts`, and markdown's `getLayout`).

### Task 4: `data-if` / `data-unless`

**Files:**
- Create: `scripts/utils/layouts/conditionals.js`, `scripts/plugins/conditional-sections.js`

**Interfaces:**
- `isSet(value) → boolean`: false for `undefined`, `null`, `''`, `false`, `[]`, and strings of only whitespace; true otherwise.
- `applyConditionals(html: string, lookup: (key: string) => { known: boolean, value?: any }) → string`
  - It returns `html` unchanged (the same string) when it contains neither `data-if` nor `data-unless`.
  - For a known key, it removes the element (`data-if` and not set, or `data-unless` and set) or strips the attribute.
  - An unknown key is left in place for a later pass.
  - It works on string fragments and on full documents. Serialization must not change bytes outside the affected elements, so use a tag-matching string transform, not a DOM re-serialize.
- Layout time (`render.js`):
  - `known` for keys in `pageData`, for `slot:*` (set means non-blank), and for keys in `data`.
  - Keys whose first segment is the repeat alias of an enclosing `data-repeat` are unknown here.
- `repeat-collection.js`: inside each repeated item, it resolves `alias.x` keys against the item.
- Late pass `conditionalSections({ file, data, allowType })`: every remaining key is known, from `{ ...data, ...file.frontMatter }`. Missing means not set (ruling P5).
